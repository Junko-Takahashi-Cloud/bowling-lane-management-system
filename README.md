# bowling-lane-management-system

## スポーツボウリング場運営システム・第三弾「店舗・スタッフ管理システム」

第一弾・第二弾で構築した予約システムを土台に、店舗運営側（管理者・スタッフ）が日々の業務を行うための管理機能を追加した拡張プロジェクトです。

既存の予約システムを作り直すのではなく、**既存モデル・APIとの整合性を維持しながら、店舗運営に必要な機能を段階的に追加する**方針で開発しています。

---

## プロジェクト概要

「スポーツとしてボウリングを楽しめる場所」をコンセプトにした、4レーン規模・地域密着型のスポーツボウリング場を想定した運営システムです。

大会（トーナメント）は開催せず、初心者教室を軸に、初心者から競技者まで継続的にボウリングを楽しめる環境を想定しています。

システム全体は4段階のロードマップで構成しており、本リポジトリは**第三弾（Phase 3）**にあたります。

| 段階 | 内容 | 状態 |
|---|---|---|
| 第一弾 | レーン予約システム（基盤） | 完成済み |
| 第二弾 | 予約システムの発展（教室コース・団体申込・貸切予約等） | 完成済み |
| **第三弾（本リポジトリ）** | **店舗・スタッフ管理システム** | **Phase 3-1 / 3-2 完了** |
| 第四弾 | 会員・成長支援システム | 構想段階 |

---

## 第三弾の位置づけ

第一弾・第二弾では、主に**お客様が予約するための仕組み**を構築しました。

第三弾では、その予約を店舗側で実際に運用するための仕組みを追加しています。

```text
第一弾
レーン予約の基盤
        ↓
第二弾
教室・団体・貸切など予約機能の拡張
        ↓
第三弾
店舗運営・スタッフ業務
        ↓
第四弾
会員管理・投球記録・成長支援
```

第三弾は、予約システムと店舗現場をつなぐ**運営側のレイヤー**として位置づけています。

# 第三弾で実装した機能

## Phase 3-1：店舗運営MVP

「現場が最低限回ること」を目的とした機能を実装しています。

### スタッフ認証

- 4桁PINによるスタッフログイン
- `Staff`テーブルによるスタッフ管理
- JWTによる認証
- `is_active`による在籍・無効状態の管理
- 無効化されたスタッフは、有効なJWTを保持していてもAPI利用不可

### レーン状態管理

個別レーンの状態を管理します。

- 空き
- 使用中
- 故障中
- メンテナンス中

レーンの状態に応じて予約・チェックインなどの処理を制御します。

### 来店受付・チェックイン／チェックアウト

店舗での来店受付を想定し、

- チェックイン
- レーン利用
- チェックアウト

までの流れを管理します。

体験利用など、事前予約を伴わない利用にも対応できる構成としています。

### レンタル管理

店舗で貸し出す、

- レンタルシューズ
- レンタルボール

を利用記録・料金計算の対象として管理します。

### 決済・料金管理

時間単価制を前提として料金を管理します。

- レーン利用料金
- レンタル料金
- 教室料金
- 教室は先払い
- レーン時間貸しは後払い

料金マスタを分離し、料金設定を一元管理できる構成としています。

### 教室出欠管理

初心者教室は全5回のコースを想定しています。

出欠は**グループ単位**で管理し、第三弾では個人単位の会員カルテ管理までは行いません。

個人単位の詳細な成長記録は第四弾で扱う予定です。

### 当日ダッシュボード

店舗スタッフが当日の状況を把握できるよう、

- レーン状態
- 当日の予約
- 教室セッション

などをまとめて取得できるダッシュボードAPIを実装しています。

# Phase 3-2：運用機能の拡張

Phase 3-2では、店舗運営における変更対応を中心に機能を追加しました。

## レーンアサイン変更

教室セッションに対して、使用するレーンペアを割り当てます。

4レーン構成のため、

- `1` → 1・2番レーン
- `3` → 3・4番レーン

という先頭レーン番号方式で管理しています。

### 対応API

```text
POST  /api/v1/class_courses/{course_id}/sessions/assign-lane-pair
PATCH /api/v1/class_sessions/{session_id}/lane-pair
```

コース全体の5セッションへの一括設定と、個別セッションの変更に対応しています。

なお、第三弾では、

- 教室が入っていない時間帯の自動開放
- 募集締切による自動開放

などの高度な自動化までは実装していません。

# 予約変更機能

予約作成時と同じ基本ルールを適用しながら、既存予約の日時・レーンセットを変更できるようにしました。

予約変更には、利用者向けとスタッフ向けの2つのAPIを用意しています。

## User用予約変更API

```text
PATCH /reservations/{reservation_id}
```

予約した本人、または管理者（`admin`）が利用します。

- 一般利用者：自分の予約のみ変更可能
- `admin`：管理権限により対象予約を変更可能

## Staff用予約変更API

```text
PATCH /api/v1/staff/reservations/{reservation_id}
```

店舗スタッフが来店者対応を行うための専用APIです。

スタッフは予約所有者を問わず、店舗で必要な予約変更を行える設計としています。

---

# 認証・権限設計

本システムでは、**User系とStaff系を別の認証ドメインとして分離**しています。

| | 利用者 | 管理者 | スタッフ |
|---|---|---|---|
| 実体 | `User` | `User` | `Staff` |
| 識別 | `role=user / competitor` | `role=admin` | `Staff` |
| ログイン | メール＋パスワード | メール＋パスワード | 4桁PIN |
| 認証 | User JWT | User JWT | Staff JWT |
| JWTクレーム | `sub` | `sub` | `staff_id` |
| 認証依存 | `get_current_user` | `get_current_user` | `get_current_staff` |

### 管理者とスタッフは別の存在

`admin`は既存の`User`テーブルにおける管理権限です。

一方、`Staff`は店舗現場で業務を行うスタッフ用の別テーブルです。

つまり、

```text
User
 ├─ user
 ├─ competitor
 └─ admin

Staff
 └─ 店舗スタッフ
```

という構造になっています。

認証トークンのクレームも、

```text
User   → sub
Staff  → staff_id
```

と分離しています。

これにより、User用トークンとStaff用トークンが別の認証処理に誤って利用されることを防いでいます。

### Staffの無効化

`Staff.is_active`で在籍状態を管理しています。

スタッフが無効化された場合、すでにJWTを取得済みであっても、`get_current_staff`で`is_active`を確認するためAPIアクセスは拒否されます。

確認した結果：

```text
401 Unauthorized
スタッフ認証情報が無効です
```

となります。

# 予約変更の設計

## 更新ロジックの共通化

User用APIとStaff用APIで予約変更処理を別々に実装すると、将来的に検証ルールが片方だけ変更される可能性があります。

そのため、認証・権限判定と実際の予約更新処理を分離しました。

```text
User用API
    ↓
本人 / admin の権限チェック
    ↓
_apply_reservation_update()
    ↓
共通の検証・更新処理


Staff用API
    ↓
Staff認証
    ↓
所有者チェックなし
    ↓
_apply_reservation_update()
    ↓
共通の検証・更新処理
```

この構成により、UserとStaffの両方で同じ予約変更ルールを利用します。

---

# 予約変更時の検証

## 過去日時チェック

予約作成・変更のどちらでも、日付だけではなく**開始時刻まで含めて過去日時を判定**します。

例えば、

```text
2026-08-14 18:00
```

の時点で、

```text
2026-08-14 17:00
```

への変更は拒否されます。

予約変更では部分更新を採用しているため、未指定項目は既存予約の値を利用した上で検証します。

過去日時の場合：

```text
422 Unprocessable Content
過去の日時には変更できません
```

を返します。

---

# 予約重複チェック

予約作成と予約変更で同じ重複判定ロジックを利用しています。

```text
_has_overlap()
```

で時間帯の重複を確認します。

### E001：レーンセットの重複

同じレーンセット・同じ日時で、既存予約と時間帯が重複していないかを確認します。

### E002：利用者の重複

同一利用者が、別のレーンセットを含めて同じ時間帯に複数予約を持っていないかを確認します。

### 自分自身との重複を除外

予約変更時には、変更対象となっている予約自身を重複判定から除外する必要があります。

そのため、

```text
exclude_reservation_id
```

を追加しました。

これにより、

```text
予約8を予約8自身と比較して重複扱いする
```

という誤判定を防いでいます。

---

# 教室予約（class）の変更禁止

`reservation_type="class"`の予約は、通常の予約変更APIでは変更できません。

理由は、第二弾の教室コース作成時に、

```text
Reservation
      ↕
ClassSession
```

が同じ日時情報を前提として関連付けられているためです。

`Reservation`だけを変更すると、`ClassSession`との整合性が崩れる可能性があります。

そのため、教室予約を通常の予約変更APIから変更しようとすると、

```text
409 Conflict
教室予約(class)はこのAPIでは変更できません。
```

となります。

教室日程そのものを変更する場合は、`ClassSession`との整合性を含めた別の仕組みが必要になるため、今回のスコープには含めていません。

# Swaggerによる動作確認

実装後はFastAPIのSwagger UIを利用して、正常系だけでなく異常系・権限系も確認しました。

## 正常系

- Userによる予約変更
- Staffによる予約変更
- Staffによる他ユーザー予約の変更
- レーンアサイン変更
- スタッフPINログイン
- 各管理APIの正常レスポンス確認

## 異常系・権限系

### 401 Unauthorized

- 認証情報なし
- 不正なJWT
- UserトークンによるStaff専用APIへのアクセス
- 無効化されたStaffによるアクセス

### 409 Conflict

- レーンセット・時間帯の重複
- 利用者の時間帯重複
- `class`予約の変更
- 予約変更時の重複チェック

### 422 Unprocessable Content

- 過去日時への変更
- `end_time <= start_time`
- 不正な時間形式
- 時間単位などの入力バリデーション

今回の予約変更テストでは、実際に

```text
200 OK
409 Conflict
422 Unprocessable Content
401 Unauthorized
```

を確認し、正常系・異常系・認証系が意図したルールで動作することを確認しています。

## 第三弾拡張②：ギア登録機能（セルフ登録／スタッフ代理登録）

第三弾（店舗運営システム）における拡張機能として、  
会員のマイギア（ボール・シューズ）を登録・管理する仕組みを追加しました。

この機能は第四弾「会員管理・成長支援システム」における  
ギアメンテナンス履歴・投球データ紐付けの基盤となります。

---

### 機能概要

- **セルフ登録（会員本人）**  
  会員が自分のギア情報を登録可能。  
  種別（ボール／シューズ）、名称、重さ／サイズを入力。

- **スタッフ代理登録**  
  スタッフが会員IDを指定してギアを登録可能。  
  教室参加者や新規会員の初期登録を想定。

- **閲覧機能**  
  - 会員本人：自分のギア一覧を閲覧  
  - スタッフ：任意会員のギア一覧を閲覧

---

### データモデル

| カラム名 | 型 | 説明 |
|-----------|----|------|
| id | int | 主キー |
| user_id | int | 所有者（会員ID） |
| gear_type | str | 種別（ball / shoes） |
| name | str | ギア名称 |
| weight_or_size | str | 重さまたはサイズ |
| created_at | datetime | 登録日時 |
| updated_at | datetime | 更新日時 |

---

### API 一式

- `POST /api/v1/gears` — ギア登録  
- `GET /api/v1/gears/{user_id}` — ギア一覧取得  
- `PATCH /api/v1/gears/{gear_id}` — ギア情報更新  
- `DELETE /api/v1/gears/{gear_id}` — ギア削除  

---

### 技術構成

- FastAPI / SQLAlchemy / SQLite  
- JWT 認証（スタッフ用・会員用を分離）  
- pytest による E2E テスト（登録・閲覧・更新・削除）
